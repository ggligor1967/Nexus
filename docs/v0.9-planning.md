## 2. Final recommended model

**Option A: append-only new completed `ai_plan_run` + new revision, atomic
PostgreSQL RPC.**

Restore inserts a new `ai_plan_runs` row (`status: completed`,
`model_name: "restore"`) and a new `revisions` row (`revision_note:
"Plan restored from revision <id>, previous snapshot"`). The restored
`previous_snapshot` becomes the new current plan. Existing `ai_plan_runs` and
`revisions` rows are never mutated or deleted. The project row is intentionally
updated atomically (`status = generated`, `build_ready_acknowledged = false`).
The entire operation — run insert, revision insert, project update — is atomic
via a single `SECURITY DEFINER` Postgres function.

**Restore target**: `previous_snapshot` only. UI label: "Restore previous
version". `new_snapshot` restore, two-sided selection, and arbitrary snapshot
restore are out of scope.

## 3. Approved restore semantics

- **New run, not mutation**: restore inserts a new `ai_plan_runs` row. Existing
  runs are never modified.
- **New revision**: restore inserts a new `revisions` row capturing
  `current → restored`.
- **New current version**: the restored plan becomes the latest completed run
  and thus the visible/exportable plan.
- **Original restored-from revision preserved**: the source revision row is
  never touched. The new revision references the new restore run, not the old
  one.
- **`previous_snapshot` only**: v0.9 restores the plan that was current *before*
  the selected revision's regeneration.
- **`model_name = "restore"`**: the restore run's `model_name` is `"restore"`,
  not the source run's model name.
- **Idempotency**: restore is append-only and is not generally idempotent after
  intervening project-state changes. An immediate duplicate restore is blocked
  by the authoritative no-op guard when the target snapshot is already current:
  it returns `409 ALREADY_CURRENT` and creates no rows. If the project later
  changes again, restoring the same source revision may validly create another
  restore run and revision.

### `model_name` semantics

The restore run's `model_name` is explicitly `"restore"`.

Rationale:

- `ai_plan_run` describes the operation that created the current run. A restore
  is not an AI generation — it is a server-side state recovery operation.
- `restore_source_run_id` records the deterministically resolved predecessor
  selected under LINEAGE-RISK-001. That predecessor's AI/fixture metadata
  remains queryable while the referenced source row exists.
- The restored plan remains structurally equal to the validated source snapshot
  under native JSONB equality; byte-for-byte serialization identity is not
  claimed.

Export consequence:

After restore, deterministic Markdown export metadata will contain:

```yaml
model: "restore"
```

This is intentional and means:

- the current version was produced by a restore operation;
- the deterministically resolved predecessor's AI/fixture metadata remains
  queryable through `restore_source_run_id` while the referenced source row
  exists.

The source run's `model_name` is **not** silently reused. This keeps the export
honest about how the current plan was produced and prevents misleading metadata
like `model: "fixture"` on a plan that was never generated in this session.

## 4. Validation-before-write flow

The API route validates **before** calling the RPC. No write occurs if
validation fails. The RPC re-verifies integrity as a defense-in-depth check.

### Route validation sequence

1. Parse body. `confirm` must be `true`, otherwise **400**
   (`"Confirmation required."`).
2. `requireApiUser(supabase)` → **401** if unauthenticated.
3. `getOwnedProject(supabase, projectId, user.id)` → **404** if not owner /
   project missing.
4. Fetch the revision row through the **user/RLS client** (not admin):
   ```ts
   const { data: revision } = await supabase
     .from("revisions")
     .select("id, previous_snapshot, ai_plan_run_id")
     .eq("id", revisionId)
     .eq("project_id", projectId)
     .maybeSingle();
   ```
   → **404** if not found (RLS denies non-owner reads)
5. Require `previous_snapshot` → **409** if null
   (`"This revision has no restorable previous snapshot."`)
6. `NexusPlanSchema.safeParse(previousSnapshot)` → **422** if invalid, **no
   writes performed**
7. Early route checks (UX optimizations, not authoritative):
   - Fetch current latest completed `plan_json` (via user client). If identical
     to validated plan → **409** (`"Restored plan is already the current
     version."`)
   - Check for any `ai_plan_runs` row with `status: "running"` → **409**
     (`"A generation is currently in progress."`)
8. Call the RPC via the **admin client** with `p_project_id`,
   `p_revision_id`, `p_user_id`, `p_validated_plan` (the Zod-validated JSON).
9. Map `error.code` SQLSTATE values (see §7).
10. Return:
    ```json
    {
      "runId": "<uuid>",
      "revisionId": "<uuid>",
      "status": "completed",
      "plan": { /* NexusPlan */ }
    }
    ```

### Clarification: early route checks vs RPC checks

- Steps 7 are **UX optimizations** — they return fast, user-friendly 409s
  before the RPC round-trip.
- The RPC checks (snapshot equality, running generation, no-op, resolved source
  predecessor selection) remain **authoritative** because state can change between the
  route's fetch and the RPC's write. A concurrent generation could start after
  step 7 but before the RPC executes.
- **No writes happen before the RPC.** The route's early checks are read-only.

## 5. Final migration shape

**Migration**: `supabase/migrations/0004_restore_plan_rpc.sql` — planning
artifact only; do not create it.

### Structure

```sql
-- v0.9: Revision restore / rollback.
-- Adds a SECURITY DEFINER RPC that atomically inserts a restore ai_plan_run,
-- a restore revision, and updates project state in a single transaction.
-- Adds nullable audit columns to revisions with ON DELETE SET NULL.

-- 5a. Audit columns on revisions
ALTER TABLE public.revisions
  ADD COLUMN IF NOT EXISTS restore_source_revision_id UUID
    REFERENCES public.revisions(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS restore_source_run_id UUID
    REFERENCES public.ai_plan_runs(id) ON DELETE SET NULL;

-- 5b. Restore RPC
CREATE OR REPLACE FUNCTION public.restore_plan(
  p_project_id UUID,
  p_revision_id UUID,
  p_user_id UUID,
  p_validated_plan JSONB
)
RETURNS TABLE (
  run_id UUID,
  revision_id UUID,
  plan_json JSONB
)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog
AS $$
DECLARE
  v_revision RECORD;
  v_source_run RECORD;
  v_current_plan JSONB;
  v_running_count INTEGER;
  v_new_run_id UUID;
  v_new_revision_id UUID;
  v_producing_run RECORD;
BEGIN
  -- 1. Lock the revision row
  SELECT id, project_id, previous_snapshot, ai_plan_run_id
    INTO v_revision
  FROM public.revisions
  WHERE id = p_revision_id
    AND project_id = p_project_id
  FOR UPDATE;

  IF NOT FOUND THEN
    RAISE SQLSTATE 'P4001' USING MESSAGE = 'NOT_FOUND';
  END IF;

  -- 2. Internal ownership check + lock project row
  PERFORM 1
  FROM public.projects
  WHERE id = p_project_id
    AND user_id = p_user_id
  FOR UPDATE;

  IF NOT FOUND THEN
    RAISE SQLSTATE 'P4001' USING MESSAGE = 'NOT_FOUND';
  END IF;

  -- 3. Verify previous_snapshot exists
  IF v_revision.previous_snapshot IS NULL THEN
    RAISE SQLSTATE 'P4002' USING MESSAGE = 'NO_RESTORABLE_SNAPSHOT';
  END IF;

  -- 4. Verify passed plan matches stored previous_snapshot (native JSONB equality)
  IF p_validated_plan IS DISTINCT FROM v_revision.previous_snapshot THEN
    RAISE SQLSTATE 'P4003' USING MESSAGE = 'SNAPSHOT_MISMATCH';
  END IF;

  -- 5. Reject if a running ai_plan_run exists (concurrency guard)
  SELECT count(*) INTO v_running_count
  FROM public.ai_plan_runs
  WHERE project_id = p_project_id
    AND status = 'running';

  IF v_running_count > 0 THEN
    RAISE SQLSTATE 'P4004' USING MESSAGE = 'GENERATION_IN_PROGRESS';
  END IF;

  -- 6. No-op protection: compare with current completed plan
  SELECT plan_json INTO v_current_plan
  FROM public.ai_plan_runs
  WHERE project_id = p_project_id
    AND status = 'completed'
  ORDER BY completed_at DESC, id DESC
  LIMIT 1;

  IF v_current_plan IS NOT NULL
     AND v_current_plan = p_validated_plan THEN
    RAISE SQLSTATE 'P4005' USING MESSAGE = 'ALREADY_CURRENT';
  END IF;

  -- 7. Resolve the source predecessor: latest matching completed predecessor
  --    under the same compound chronology used to select the current plan.
  --    Guard: if the revision's ai_plan_run_id is null or the producing run
  --    is absent or its completed_at is null, raise SOURCE_RUN_UNRESOLVABLE.
  IF v_revision.ai_plan_run_id IS NULL THEN
    RAISE SQLSTATE 'P4006' USING MESSAGE = 'SOURCE_RUN_UNRESOLVABLE';
  END IF;

  SELECT id, completed_at INTO v_producing_run
  FROM public.ai_plan_runs
  WHERE id = v_revision.ai_plan_run_id;

  IF NOT FOUND OR v_producing_run.completed_at IS NULL THEN
    RAISE SQLSTATE 'P4006' USING MESSAGE = 'SOURCE_RUN_UNRESOLVABLE';
  END IF;

  SELECT * INTO v_source_run
  FROM public.ai_plan_runs
  WHERE project_id = p_project_id
    AND status = 'completed'
    -- Implementation-time verification: use a compound completed_at + id
    -- comparison so the candidate orders before the producing run. The exact
    -- row-comparison syntax must be verified against the deployed database.
    AND (completed_at, id) < (v_producing_run.completed_at, v_producing_run.id)
    AND plan_json = v_revision.previous_snapshot
  ORDER BY completed_at DESC, id DESC
  LIMIT 1;

  IF NOT FOUND THEN
    RAISE SQLSTATE 'P4006' USING MESSAGE = 'SOURCE_RUN_UNRESOLVABLE';
  END IF;

  -- 8. Insert restore ai_plan_run
  -- IMPLEMENTATION-TIME VERIFICATION REQUIRED: prefer omitting explicit ids
  -- only after confirming the existing table defaults, then use RETURNING id.
  INSERT INTO public.ai_plan_runs (
    project_id, concept_input_id, model_name,
    status, plan_json, completed_at
  )
  VALUES (
    p_project_id, v_source_run.concept_input_id,
    'restore', 'completed', p_validated_plan, now()
  )
  RETURNING id INTO v_new_run_id;

  -- 9. Insert restore revision with structured audit metadata
  INSERT INTO public.revisions (
    project_id, ai_plan_run_id, revision_note,
    previous_snapshot, new_snapshot,
    restore_source_revision_id, restore_source_run_id
  )
  VALUES (
    p_project_id, v_new_run_id,
    'Plan restored from revision ' || p_revision_id::text || ', previous snapshot',
    v_current_plan, p_validated_plan,
    p_revision_id, v_source_run.id
  )
  RETURNING id INTO v_new_revision_id;

  -- 10. Update project state
  UPDATE public.projects
  SET status = 'generated',
      build_ready_acknowledged = false
  WHERE id = p_project_id
    AND user_id = p_user_id;

  RETURN QUERY
  SELECT v_new_run_id, v_new_revision_id, p_validated_plan;
END;
$$;

-- 5c. Privilege hardening
REVOKE EXECUTE ON FUNCTION public.restore_plan(UUID, UUID, UUID, JSONB) FROM PUBLIC;
REVOKE EXECUTE ON FUNCTION public.restore_plan(UUID, UUID, UUID, JSONB) FROM anon;
REVOKE EXECUTE ON FUNCTION public.restore_plan(UUID, UUID, UUID, JSONB) FROM authenticated;
GRANT EXECUTE ON FUNCTION public.restore_plan(UUID, UUID, UUID, JSONB) TO service_role;
```

## 6. RPC privilege model

### Why `p_user_id` cannot be supplied by a direct client call

- The function is `SECURITY DEFINER`: it executes with the privileges of the
  Postgres owner, not the caller.
- `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` ensures that **only
  `service_role`** can call the function.
- The Supabase client (anon + session) authenticates as `authenticated`, which
  is revoked. Even if a malicious client constructed a raw RPC call with an
  arbitrary `p_user_id`, the database would reject the call because
  `authenticated` has no `EXECUTE` privilege.
- The API route supplies `auth.user.id` from the verified session.
- The internal ownership check (`user_id = p_user_id`) is defense in depth
  against server-route bugs, parameter mix-ups, and accidental cross-project
  calls.
- Compromise of the service-role credential is outside this control's threat
  boundary. A fully compromised credential could supply a matching user id and
  requires credential rotation and incident response; `p_user_id` does not
  protect against that compromise.

### Privilege summary

| Role | Can execute `restore_plan`? |
|---|---|
| `PUBLIC` | No (revoked) |
| `anon` | No (revoked) |
| `authenticated` | No (revoked) |
| `service_role` | Yes (granted) |

### Search-path hardening

The RPC uses `SET search_path = pg_catalog`. A writable application schema is
not retained in a `SECURITY DEFINER` search path unless implementation-time
inspection proves it is required and safe.

Application tables are schema-qualified (`public.revisions`,
`public.ai_plan_runs`, `public.projects`). The planning SQL does not claim a
verified schema for a UUID generator. At implementation time, either confirm
the existing verified table defaults and omit explicit ids with `INSERT ...
RETURNING id`, or inspect `pg_proc` / the deployed Supabase schema and
schema-qualify the actual trusted UUID generator.

Direct `authenticated`/`anon` RPC execution remains denied by the
`REVOKE EXECUTE` grants. Direct service-role execution is an intentionally
trusted administrative capability, is not exposed to browser clients, and
requires operational protection of the service-role credential.

## 7. SQLSTATE error contract

The RPC uses custom SQLSTATE codes, not free-form exception messages. The API
route maps `error.code` (the SQLSTATE), not `error.message`.

### Custom SQLSTATE codes

| SQLSTATE | Meaning | HTTP status | Response body |
|---|---|---|---|
| `P4001` | NOT_FOUND — project or revision not found / not owned | 404 | `{ "error": "Project or revision not found." }` |
| `P4002` | NO_RESTORABLE_SNAPSHOT — `previous_snapshot` is null | 409 | `{ "error": "This revision has no restorable previous snapshot." }` |
| `P4003` | SNAPSHOT_MISMATCH — passed plan does not match stored `previous_snapshot` | 500 | `{ "error": "Snapshot integrity check failed." }` |
| `P4004` | GENERATION_IN_PROGRESS — a `running` `ai_plan_run` exists | 409 | `{ "error": "A generation is currently in progress." }` |
| `P4005` | ALREADY_CURRENT — target plan is already the current plan | 409 | `{ "error": "Restored plan is already the current version." }` |
| `P4006` | SOURCE_RUN_UNRESOLVABLE — resolved source predecessor cannot be safely resolved | 409 | `{ "error": "Could not resolve the source plan run for this snapshot." }` |
| (any other) | Unknown error | 500 | `{ "error": "Restore failed." }` |

The route switches on `error.code`. The `MESSAGE` in the `RAISE` statement is
for human-readable logging only and is not parsed by the route.

### Example RPC error

```sql
RAISE SQLSTATE 'P4001' USING MESSAGE = 'NOT_FOUND';
```

The Supabase admin client surfaces this as an error object where
`error.code === 'P4001'`. The route maps `P4001` → 404.

## 8. Source-run resolution

### Algorithm

The **resolved source predecessor** is the latest matching completed
predecessor under the repository's deterministic chronology. It is a
reconstruction for legacy data, not an assertion of exact historical
provenance.

1. The selected revision's `ai_plan_run_id` points to the regeneration run
   that produced `new_snapshot`; existing revision rows do not directly store
   the run id that produced `previous_snapshot`.
2. **Guard**: if `v_revision.ai_plan_run_id` is null → `P4006`
   (`SOURCE_RUN_UNRESOLVABLE`). The producing run is absent and the timeline
   cannot be established.
3. Retrieve the producing run's `id` and `completed_at`:
    ```sql
    SELECT id, completed_at FROM public.ai_plan_runs
    WHERE id = v_revision.ai_plan_run_id;
    ```
    If not found or `completed_at` is null → `P4006`.
4. Query for the latest completed predecessor on this project where:
    - `project_id` matches
    - `status = 'completed'`
    - it orders before the producing run under `(completed_at ASC, id ASC)`
    - `plan_json = v_revision.previous_snapshot` using **native JSONB equality**
      (`=`)
5. `ORDER BY completed_at DESC, id DESC` + `LIMIT 1` — deterministic
   selection of the latest matching predecessor.
6. If found: use its `concept_input_id` and its `id` (for
   `restore_source_run_id`).
7. If not found: `P4006` → 409, write nothing.

Matching `previous_snapshot` against prior completed `plan_json` values is a
deterministic reconstruction. It is the best available predecessor resolution
for existing v0.5–v0.8 data, but it is not cryptographic or absolute provenance.
`restore_source_run_id` records the predecessor selected by this algorithm.

### Deterministic ordering

Source selection and current-plan selection must use one consistent compound
ordering of `completed_at` + `id`. A candidate is a predecessor only when it
orders before the producing run under `(completed_at ASC, id ASC)`; the
equivalent reverse-direction selection is `ORDER BY completed_at DESC, id DESC
LIMIT 1`. Equal timestamps therefore use the `id` tie-breaker. Timestamp
ordering alone does not prove chronology. The exact SQL row-comparison syntax
is an implementation-time verification item.

### No fallback

If the resolved source predecessor cannot be resolved: `P4006` → 409, write nothing. **Never**
fall back to the latest unrelated `concept_input`.

### Missing producing-run guard

If the selected revision's `ai_plan_run_id` is null, the producing run is
absent, or the producing run's `completed_at` is null, the RPC raises
`P4006` (`SOURCE_RUN_UNRESOLVABLE`). This covers the edge case where a
revision exists but its `ai_plan_run_id` was not populated or the referenced
run was deleted. The restore is rejected cleanly with no writes.

### Why native JSONB equality

Postgres `JSONB` `=` operator performs canonical comparison: key order is
normalized, and values are compared semantically. Both `previous_snapshot` and
`plan_json` went through Supabase's JSONB encoder, so native equality is the
correct and reliable comparison.

## 9. Structured audit metadata

### New nullable columns on `revisions`

```sql
ALTER TABLE public.revisions
  ADD COLUMN IF NOT EXISTS restore_source_revision_id UUID
    REFERENCES public.revisions(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS restore_source_run_id UUID
    REFERENCES public.ai_plan_runs(id) ON DELETE SET NULL;
```

| Field | Type | Nullable | Populated by |
|---|---|---|---|
| `restore_source_revision_id` | `UUID` FK → `revisions(id)` `ON DELETE SET NULL` | Yes | Restore RPC only |
| `restore_source_run_id` | `UUID` FK → `ai_plan_runs(id)` `ON DELETE SET NULL` | Yes | Restore RPC only |

### Why nullable does not by itself prevent deletion blocking

A nullable FK still has a referential constraint. With the default
`ON DELETE NO ACTION`, deleting the referenced row (the source revision or
source run) would fail if any restore revision still references it — even
though the column is nullable. The nullable column allows the FK to be `NULL`
for normal regenerations, but does not prevent the FK from blocking deletion of
the target row.

### Why `ON DELETE SET NULL` is preferred over `NO ACTION`

- **`ON DELETE SET NULL`**: if the source revision or source run is deleted
  later, the restore revision's `restore_source_revision_id` /
  `restore_source_run_id` is set to `NULL`. The restore revision itself, its
  `revision_note`, its `previous_snapshot`, its `new_snapshot`, and its
  `ai_plan_run_id` all survive. The primary audit event is preserved.
- **`ON DELETE NO ACTION`** (the default): deleting the source row would fail
  because a restore revision still references it. This would block legitimate
  cleanup of old data and create orphaned deletion failures.
- `SET NULL` is the right product choice: the restore revision is the
  authoritative audit record. The source pointers are convenience metadata. If
  the source disappears, the restore revision still tells the story via
  `revision_note` and snapshots.

### What audit information remains after the FK target is deleted

| Field | After source deletion |
|---|---|
| `restore_source_revision_id` | `NULL` |
| `restore_source_run_id` | `NULL` |
| `revision_note` | Preserved (`"Plan restored from revision <id>, previous snapshot"`) — the human-readable text still contains the source revision id |
| `previous_snapshot` | Preserved (the pre-restore plan) |
| `new_snapshot` | Preserved (the restored plan) |
| `ai_plan_run_id` | Preserved (points to the new restore run) |

The structured pointers are lost, but the `revision_note` text and the
snapshots remain. This is the correct trade-off: lose the queryable pointer,
keep the audit event.

### Normal regeneration behavior

Normal regeneration revisions (via `generate-plan`) leave both columns `NULL`.
No `NOT NULL` constraint is added. Existing rows from v0.5–v0.8 are
unaffected. The migration is purely additive.

### Why `revisions` not `ai_plan_runs`

The audit metadata answers "which revision was this restore triggered from?"
— a revision-level question. Co-locating the audit on the revision row keeps
it with the audit event itself. Adding columns to `ai_plan_runs` would
conflate AI-generation metadata with restore metadata.

### No cascading deletion

Neither FK uses `ON DELETE CASCADE`. A deleted source row sets the pointer to
`NULL`; it does not delete the restore revision. This prevents audit-chain
destruction.

## 10. Transaction sequence

All steps execute in a single Postgres transaction inside the RPC:

```
BEGIN
  1. SELECT revision FOR UPDATE                         -- lock revision row
  2. PERFORM project ownership check FOR UPDATE         -- lock project row
  3. Verify previous_snapshot is not null                -- P4002
  4. Verify p_validated_plan = previous_snapshot         -- P4003 (JSONB equality)
  5. Check no running ai_plan_run                        -- P4004
  6. Check not already current                           -- P4005
  7. Resolve source predecessor (concept_input_id, run id) -- P4006
  8. INSERT ai_plan_runs (restore run, model_name='restore')  -- write 1
  9. INSERT revisions (restore revision + audit metadata)    -- write 2
  10. UPDATE projects (status='generated', build_ready_ack=false)  -- write 3
  11. RETURN (run_id, revision_id, plan_json)
COMMIT
```

Any exception at steps 3–10 raises a SQLSTATE and the entire transaction rolls
back. No partial writes survive. The `FOR UPDATE` locks are released on
rollback.

## 11. Risk acceptance

### CONCURRENCY-RISK-001

| Field | Value |
|---|---|
| **Status** | ACCEPTED FOR v0.9 |
| **Scope** | Concurrent restore and generate-plan operations on the same project |
| **Cause** | Restore locks the project row (`FOR UPDATE`) inside the RPC, but `generate-plan` does not acquire the same lock or an advisory lock |
| **Possible effect** | Confusing chronological ordering — whichever run finishes later may become the latest completed plan; revision history may reflect concurrent user actions |
| **Expected security impact** | None |
| **Expected RLS impact** | None |
| **Expected data-loss impact** | None — both paths are append-only; neither corrupts the other's data |
| **Probability** | Low under normal UI interaction (requires user to trigger restore and regenerate within the same sub-second window) |
| **Mitigations in v0.9** | • Reject restore when a `running` `ai_plan_run` already exists (RPC check + route early check) • Disable restore UI while the page knows generation is active • Project-row `FOR UPDATE` lock inside restore RPC • Document residual race honestly |
| **Deferred follow-up** | Common `pg_advisory_xact_lock` or shared project-lock protocol for both `generate-plan` and `restore` |
| **Explicit statement** | v0.9 does **not** claim complete cross-route serialization. |

v0.9 scope does **not** modify `generate-plan`. A future change can add
advisory locking to both routes if the race becomes a real issue.

### LINEAGE-RISK-001

| Field | Value |
|---|---|
| **Status** | ACCEPTED FOR v0.9 |
| **Scope** | Reconstruction of the source predecessor for legacy revision rows |
| **Cause** | Revisions store the run producing `new_snapshot`, but not the run producing `previous_snapshot` |
| **Mitigation** | • Native JSONB equality • Same project • Completed predecessor only • Compound `completed_at` + `id` ordering • No unrelated `concept_input` fallback • Structured `restore_source_run_id` recorded on new restore revisions |
| **Possible effect** | When multiple prior runs contain identical plans, the latest matching predecessor is selected |
| **Security impact** | None expected |
| **RLS impact** | None expected |
| **Data-loss impact** | None expected |
| **Explicit statement** | `restore_source_run_id` represents the deterministically resolved predecessor, not guaranteed historical provenance for legacy snapshots. |

```json
{
  "runId": "<uuid>",
  "revisionId": "<uuid>",
  "status": "completed",
  "plan": { /* NexusPlan */ }
}
```

### Route flow

1. Parse body. `confirm` must be `true`, otherwise **400**.
2. `requireApiUser(supabase)` → **401** if unauthenticated.
3. `getOwnedProject(supabase, projectId, user.id)` → **404** if not owner /
   project missing.
4. Fetch revision through user/RLS client
   (`eq("id", revisionId).eq("project_id", projectId)`) → **404** if not found.
5. Require `previous_snapshot` → **409** if null.
6. `NexusPlanSchema.safeParse(previousSnapshot)` → **422** if invalid (no
   writes).
7. Early route checks (UX optimizations, not authoritative):
   - No-op check: compare validated plan against current completed `plan_json`
     → **409** if identical.
   - Running-generation check: query for `status: "running"` → **409** if
     found.
8. Call admin/service-role RPC with `p_project_id`, `p_revision_id`,
   `p_user_id`, `p_validated_plan`.
9. Map `error.code` SQLSTATE values (see §7). Unknown codes → **500**.
10. Return `{ runId, revisionId, status: "completed", plan }`.

### Clarification

- Steps 7 are UX optimizations. The RPC checks (steps 3–6 in the transaction)
  remain authoritative because state can change between the route's fetch and
  the RPC's write.
- **No writes happen before the RPC.**

## 13. UX

- **Button label**: "Restore previous version"
- **Action placement**: revision snapshot route only
  (`/projects/[id]/revisions/[revisionId]`)
- **Confirmation**: always required

### Exact confirmation copy

> Restoring will create a new current plan from the previous version. Your
> current plan and all existing history will be preserved. Build-ready
> acknowledgement will be reset.

### Confirmation dialog contents

- The exact copy above.
- Source revision timestamp (already available on the snapshot page as
  `revision.created_at`).
- **No version number** — the snapshot route does not have the full revision
  list available, so "Revision N" cannot be derived reliably without an
  additional query. Do not invent a numbering scheme.

### After success

- Redirect to the project page (`/projects/[id]`).
- Show "Plan restored." banner.
- Restored plan is current (visible in `GeneratedPlanView`).
- `build_ready_acknowledged` is `false` (acknowledgement reset).

### No silent overwrite

Confirmation is always required. The restore action is never automatic.

## 14. Build-ready and safety semantics

- `build_ready_acknowledged` resets to `false` inside the RPC transaction
  (step 10).
- If the restored plan is critical, the user must re-acknowledge before
  build-ready is available.
- **SEC-002 interaction**: the PATCH build-ready route checks for a completed
  validated plan. The restore run is `status: completed` with valid
  `plan_json`, so SEC-002 passes naturally. No change to the PATCH route.
- **Fail-closed**: any RPC exception → 4xx/500, no writes persist, current
  plan unchanged, acknowledgement unchanged.

## 15. Test strategy

### Functional tests

| Test | What it verifies |
|---|---|
| RESTORE-001 | Successful `previous_snapshot` restore: new completed run with `model_name: "restore"`, restored plan becomes current, new revision with `revision_note: "Plan restored from revision <id>, previous snapshot"` |
| RESTORE-002 | Structured source metadata populated: `restore_source_revision_id` and `restore_source_run_id` set on the restore revision |
| RESTORE-003 | Prior history unchanged: source revision row unchanged, all prior revisions and runs unchanged |
| RESTORE-004 | `concept_input_id` on restore run matches the resolved predecessor's `concept_input_id`, not an unrelated latest concept input |
| RESTORE-005 | Cross-user restore denied: User B gets 404 for User A's project + revision |
| RESTORE-006 | Cross-project revision denied: revision from project X → 404 on project Y |
| RESTORE-007 | `confirm: false` or missing → 400, no writes |
| RESTORE-008 | `previous_snapshot` is null → 409, no writes |
| RESTORE-009 | No-op: restoring a plan that is already current → 409, no writes |
| RESTORE-010 | Resolved source predecessor unavailable (including null `ai_plan_run_id` or missing producing run) → 409, no writes |
| RESTORE-011 | Generation running → 409, no writes |
| RESTORE-012 | Critical-risk acknowledgement reset: after restoring a critical plan, `build_ready_acknowledged` is `false`, checkbox unchecked, build-ready disabled until re-acknowledged |
| RESTORE-013 | Normal regeneration revisions have `restore_source_revision_id = NULL` and `restore_source_run_id = NULL` |
| RESTORE-014 | Export after restore: Markdown export contains `model: "restore"` |
| RESTORE-015 | Client direct writes remain denied: authenticated client cannot INSERT into `ai_plan_runs` or `revisions` (SEC-003 / REV-SEC-001 coverage continues) |
| RESTORE-016 | v0.8 revision/diff/export tests remain green (REV-UI-001, REV-RLS-001, diff-unit, markdown-unit) |

### Atomicity tests

**Method**: temporary test-only database triggers, created in test setup and
dropped in teardown. No public production fault flags. No `p_fault_at`
parameters in the production RPC. No wrapper that only fails before calling the
production RPC.

#### A. Revision-insert rollback proof

| Step | Action |
|---|---|
| Setup | Create a temporary trigger on `public.revisions` that raises a known exception only for the controlled atomicity-test project id and when `revision_note` starts with `"Plan restored from revision"` |
| Act | Call the production `restore_plan` RPC via the admin client |
| Why this works | The `ai_plan_run` INSERT (step 8 in the transaction) happens before the `revisions` INSERT (step 9). The trigger fires on the revision insert, after the run insert has already executed. |
| Assert | • No restore `ai_plan_run` persisted (count unchanged) • No restore revision persisted (count unchanged) • Project `status` unchanged • `build_ready_acknowledged` unchanged • No partial audit metadata |
| Teardown | Drop the temporary trigger |

**Proves**: a failure after the first write (run insert) rolls back the run
insert. The transaction is atomic — no partial row survives.

#### B. Project-update rollback proof

| Step | Action |
|---|---|
| Setup | Create a temporary trigger on `public.projects` that raises a known exception only for the controlled atomicity-test project id and for the expected restore state transition (`status = 'generated' AND build_ready_acknowledged = false`) |
| Act | Call the production `restore_plan` RPC via the admin client |
| Why this works | The `ai_plan_run` INSERT (step 8) and `revisions` INSERT (step 9) happen before the `projects` UPDATE (step 10). The trigger fires on the project update, after both earlier writes have executed. |
| Assert | • No restore run persisted • No restore revision persisted • No partial audit metadata • Project `status` unchanged • `build_ready_acknowledged` unchanged |
| Teardown | Drop the temporary trigger |

**Proves**: a failure after the first two writes (run + revision) rolls back
both. No partial audit row survives.

#### C. Cleanup

- Atomicity trigger tests run serially and do not run in parallel with
  functional restore tests.
- Use an isolated local/CI Supabase database.
- Teardown runs even when assertions fail, drops all test triggers/functions,
  and verifies that those triggers/functions no longer exist.
- Test triggers must never appear in production migrations.

#### Execution-mechanism clarification

Trigger/function DDL must be executed through `psql` or another SQL-capable
command verified against the pinned Supabase CLI and CI environment, targeting
the isolated test database. The implementation plan must verify the exact
available command/tool. Ordinary supabase-js/PostgREST cannot execute arbitrary
DDL — PostgREST exposes stored functions, not ad-hoc DDL execution. No test-only
trigger/function appears in production migrations.

### Security tests

| Test | What it verifies |
|---|---|
| RESTORE-SEC-001 | `authenticated` client cannot execute `restore_plan` RPC directly (EXECUTE revoked) |
| RESTORE-SEC-002 | `anon` cannot execute `restore_plan` RPC directly |
| RESTORE-SEC-003 | Direct `anon` and `authenticated` RPC execution is denied; the server API route can execute through its service-role client; direct service-role execution is an intentionally trusted administrative capability not exposed to browser clients, and credential protection is an operational requirement |
| RESTORE-SEC-004 | Arbitrary `p_user_id` cannot be exploited from `authenticated` or `anon` roles (EXECUTE denied) |

## 16. Candidate architecture comparison

| Dimension | A. New run + new revision (atomic RPC) | B. Mutate current run/project | C. Separate restore-event model |
|---|---|---|---|
| User value | High — recoverable, history complete, diff works | Medium — simpler but destroys audit trail | High, but over-engineered |
| Auditability | Excellent — atomic RPC + structured `restore_source_*` columns with `ON DELETE SET NULL` | Poor — overwrites trail | Excellent, but needs new table + RLS |
| Security | Strong — `SECURITY DEFINER`, `REVOKE EXECUTE` from PUBLIC/anon/authenticated, `GRANT` to service_role only, `SET search_path = pg_catalog`, internal ownership check, SQLSTATE error contract | Weaker — mutates server-controlled rows | Strong, but new RLS surface |
| Atomicity | Guaranteed by Postgres transaction; proven by temporary-trigger fault injection | Not atomic without explicit wrapper | Guaranteed, but over-engineered |
| Concurrency | `FOR UPDATE` locks + running-generation guard; bounded residual race documented and accepted (CONCURRENCY-RISK-001) | No concurrency protection | Same as A but more complex |
| Error contract | Typed SQLSTATE codes mapped to HTTP status | Fragile free-form messages | Same as A |
| Implementation surface | One migration (RPC + 2 nullable columns), one API route, one UI button + dialog | Medium — fragile mutation | Large — new table, RLS, queries, UI |
| Migration need | One minimal migration (`0004`) | None, but fragile | Required — new table + RLS |
| Regression risk | Low — purely additive | High — breaks export/SEC-002/diff assumptions | Medium — larger surface |
| Recommendation | **Recommended** | Not recommended | Deferred |

## 18. Remaining unresolved decisions

1. **`raw_output` on the restore run**: `null` for v0.9.
   `model_name: "restore"` + structured audit columns are sufficient. If the
   reviewer wants a marker, `{"source":"restore"}` is a minor addition.
   **Recommendation**: `null`.

2. **Version number on the snapshot page**: not shown. The snapshot route does
   not query the full revision list, so "Revision N" is not reliably available.
   The confirmation dialog shows the revision timestamp only. If the reviewer
   wants the version number, a minor query addition to the snapshot route is
   needed — deferred.

3. **Advisory lock for cross-route serialization**: deferred.
   CONCURRENCY-RISK-001 is accepted for v0.9. A follow-up can add
   `pg_advisory_xact_lock` to both `generate-plan` and `restore` if the race
   becomes a real issue.

4. **Should the RPC return `restore_source_revision_id` and
   `restore_source_run_id` in the response?**: No. The response stays minimal:
   `{ runId, revisionId, status, plan }`. The route already knows the
   `revisionId` and can query the new revision row if needed.

5. **Index on `restore_source_*` columns**: no index for v0.9. These columns
   are for audit/queryability, not hot-path lookups. An index can be added
   later if query patterns demand it.
